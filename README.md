
# ガチャ履歴APIにおける大量データ検索のパフォーマンス検証レポート

本プロジェクトは、将来的な大規模ユーザーの同時接続およびデータ蓄積を見据え、ゲームサーバーにおける低遅延なデータ送受信を共通管理するための検証環境の構築、およびクエリ（SQL命令）の最適化を行った記録です。

開発・検証においては、処理時間をナノ秒・ミリ秒単位でプロファイリングする「客観的分析」と、ボトルネックの原因を特定する「要素分解」のアプローチを徹底しました。

---

## 1. 開発環境・使用技術
* **バックエンド言語**: Go言語 (Version 1.2x)
* **Webフレームワーク**: Gin
* **データベース**: MySQL (Version 8.0)
* **接続ドライバ**: go-sql-driver/mysql

---

## 2. 検証環境の構築（直面した課題と解決策）

サービス中期フェーズの高負荷環境を再現するため、データベース内に10万件の模擬ガチャ履歴データ（ログ）の流し込みを行いました。その際、以下の技術的課題に直面し、最適化を行いました。

### 直面したボトルネック
* **課題**: 
  * 1件ずつデータを保存する設計のまま10万回のループ処理を実行したところ、ハードディスクへの書き込み（I/O負荷）が限界に達しました。
  * 結果、MySQLの制限時間である30秒を超過し、強制切断エラーが発生しました。
  * `Error Code: 2013. Lost connection to MySQL server during query`

### 要素分解によるアプローチと解決策
* **分析**: 
  * 遅延の要因は通信速度ではなく、「1件ごとに発生するディスクへの書き込み確定処理（コミット）」であると特定しました。
* **対策**: 
  * データベースの「トランザクション機能（`START TRANSACTION` / `COMMIT`）」を導入。
  * 10万件のデータをメモリ上で一時的に一括処理し、最後に1回だけディスクへ書き込む設計へ変更しました。
* **成果**: 
  * 30.000秒でタイムアウト（エラー強制遮断）していた処理時間が、**1.250秒へと短縮**。
  * 不備のない正確な100,000件の負荷検証環境の構築を完了しました。

## 3. 検索パフォーマンス比較実験（Before / After）

構築した10万件のデータ群から、特定のユーザーIDに紐づくガチャ履歴（ヒット件数: 83件）を抽出するAPIの応答速度（処理時間）をプロファイリング機能で実測・比較しました。

### 実測結果の客観的データ

| 項目 | 改善前（Before） | 改善後（After） | 改善効果 |
| :--- | :--- | :--- | :--- |
| **データベースの状態** | インデックス（目次）なし | **インデックス（目次）あり** | `user_id` に対する索引の適用 |
| **APIの処理時間** | **13.3687 ms** (ミリ秒) | **502.8 µs** (マイクロ秒) | **処理時間を約96%削減** |
| **内部の走査アルゴリズム**| フルスキャン（全件走査） | **インデックススキャン（ピンポイント抽出）**| **約26.5倍の高速化を達成** |
| **サーバーへの負荷** | 高（全データ10万件を走査） | **小（インデックスから直接アクセス）** | 大規模同時接続時の安定性向上 |

### 構造の要素分解
* **Before（13.3687ms）の正体**:
  * 検索の基準となるインデックスが存在しないため、MySQLは10万件のデータを先頭から最終行まで全件走査（フルテーブルスキャン）していました。
  * 単一の検索としてはミリ秒単位ですが、大規模ゲーム環境においてはサーバーリソースを長時間拘束するため、遅延の決定的な原因となると考えました。
* **After（502.8µs）の正体**:
  * `ALTER TABLE gacha_logs ADD INDEX idx_user_id (user_id);` を実行し、ユーザーID専用のインデックスを物理的に作成しました。
  * これにより、MySQLは10万件の中から目的の83件へと直接アクセス可能になり、処理時間をマイクロ秒単位へと短縮しました。

## 4. 開発アプローチと検証プロセス（考察）

### Google Geminiを活用した「バイブコーディング」の実践
本プロジェクトにおけるコード基盤の構築およびプロファイリングの実施にあたっては、Google Geminiを開発パートナーとして全面的に組み込んだ「バイブコーディング（Vibe Coding）」を採用しました。

文法チェックや定型コードの記述といった定型作業に要する時間をAIによって最小化し、システム全体のアーキテクチャ設計やボトルネック分析など、本質的な思考プロセスにリソースを集中させました。
また、AIを活用することで、未経験であるGO言語の学習、バックエンドでの実験、実装プロセスを体系的に学習することができました。
### 主体的な検証による走査アルゴリズムの可視化
本プロジェクトにおける重要な検証プロセスは、私がソーシャルゲームのバックエンジニアで将来、どのような分野で活躍したいかを考えたうえで、自ら10万件のシステム上のガチャデータを作成導入し、データ処理速度の実験基盤を整えた点、そして、user_idなどの高カーディナリティのカラムに絞ったインデックス付与を行うことでの検索速度の計測を行った点にあります。
貴社の会社説明会でお伺いした、負荷分散の分野について、自分なりに考え、データベース実装までの試行錯誤しました経験に置きましては、今までの大学でのプログラミング学習を活かすことができたと考えております。
高速化の検証中、数値の推移とプログラム側のコンテキストメッセージの不一致を確認した際、データベース（MySQL）側で一度インデックスを完全に削除（`DROP INDEX`）する追加実験を独自に実施しました。これに合わせて、Go言語（`main.go`）側のメッセージを正確に定義し直し、プログラムのコンパイルおよびサーバーの再起動を行うことで、実行環境とコードの整合性を担保しました。

この厳密な検証プロセスを経たことで、ブラックボックスになりがちだったデータベースの走査アルゴリズムの挙動を、ミリ秒（13.36ms）とマイクロ秒（502.8µs）という明確な数値の差として客観的に実証しました。大規模トラフィックを扱うゲームバックエンドにおいて、リソースのハングアップを防止するためのシステム設計の本質を体系的に習得しました。
