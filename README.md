# ガチャ履歴APIにおける大量データ検索のパフォーマンス検証レポート

本プロジェクトは、将来的な大規模ユーザーの同時接続およびデータ蓄積を見据え、ゲームサーバーにおける低遅延なデータ送受信を共通管理するための検証環境の構築、およびクエリ（SQL命令）の最適化を行った記録です。

開発・検証においては、感覚的な判断を排除し、処理時間をナノ秒単位でプロファイリングする「客観的分析」と、ボトルネックの原因を特定する「要素分解」のアプローチを徹底しました。

---

## 1. 開発環境・使用技術
* **バックエンド言語**: Go言語 (Version 1.2x)
* **Webフレームワーク**: Gin
* **データベース**: MySQL (Version 8.0)
* **接続ドライバ**: go-sql-driver/mysql

---

## 2. 検証環境の構築（直面した課題と解決策）

サービス中期フェーズの高負荷環境を再現するため、データベース内に10万件の模擬ガチャ履歴データ（ログ）の流し込みを行いました。その際、以下の技術的課題に直面し、最適化を行いました。

### 直面したボトルネック（苦労した点）
* **課題**: 
  * 1件ずつ愚直にデータを保存する設計のまま10万回のループ処理を実行したところ、ハードディスクへの書き込み（I/O負荷）が限界に達しました。
  * 結果、MySQLの制限時間である30秒を超過し、強制切断エラーが発生しました。
  * `Error Code: 2013. Lost connection to MySQL server during query`

### 要素分解によるアプローチと解決策
* **分析**: 
  * 遅延の真犯人は、通信速度ではなく「1件ごとに毎回発生するディスクへの書き込み確定処理（コミット）」であると客観的に特定しました。
* **対策**: 
  * データベースの「トランザクション機能（`START TRANSACTION` / `COMMIT`）」を導入。
  * 10万件のデータをメモリ上で一時的に一括処理し、最後に1回だけディスクへ書き込む設計へ変更しました。
* **成果**: 
  * 30秒かかっても終わらなかった処理時間が、**わずか 1.250 秒へと劇的に短縮**。
  * 不備のない正確な100,000件の負荷検証環境の構築を完了しました。

## 3. 検索パフォーマンス比較実験（Before / After）

構築した10万件のデータ群から、特定のユーザーID（101番、ヒット件数: 83件）のガチャ履歴を抽出するAPIの応答速度（処理時間）をストップウォッチ機能で実測・比較しました。

### 実測結果の客観的データ

| 項目 | 改善前（Before） | 改善後（After） | 改善効果 |
| :--- | :--- | :--- | :--- |
| **データベースの状態** | インデックス（目次）なし | **インデックス（目次）あり** | `user_id` に対する索引の適用 |
| **APIの処理時間** | **17.3079 ms** (ミリ秒) | **509.5 µs** (マイクロ秒) | **処理時間を約97%削減** |
| **内部の捜索アルゴリズム**| フルスキャン（全件捜索） | **インデックススキャン（ピンポイント抽出）**| **約34倍の高速化を達成** |
| **サーバーへの負荷** | 高（書類10万枚を全手めくり） | **極小（目次から1発でアクセス）** | 大規模同時接続時の安定性向上 |

### 構造の要素分解
* **Before（17.3079ms）の正体**:
  * 検索の基準となる「目次」が存在しないため、MySQLは10万件のデータを1ページ目から最終ページまで泥臭くしらみつぶしに全件捜索（フルテーブルスキャン）していました。
  * 単一の検索としては高速に見えますが、数万人〜数百万人が同時に遊ぶ大規模ゲーム環境においては、サーバーがこの処理に拘束されるため致命的なバグや遅延の原因になります。
* **After（509.5µs）の正体**:
  * `ALTER TABLE gacha_logs ADD INDEX idx_user_id (user_id);` を実行し、倉庫の中にユーザーID専用の「目次」を物理的に作成しました。
  * これにより、MySQLは10万件の中から目的の83件へと1発でアクセス可能になり、ミリ秒の壁を突破してマイクロ秒（100万分の1秒）の世界へと突入しました。

## 4. 総括と考察

本検証を通じて、大規模トラフィックや大量のログデータを扱うゲームバックエンドにおいて、「データ永続化の仕組み」と「データ構造の最適化（インデックス設計）」がシステムの低遅延化にどれほど決定的な影響を与えるかを数値として実証しました。

この「実測値に基づいたボトルネックの発見」と「要素分解による確実な課題解決プロセス」の経験は、今後の大規模ゲーム開発におけるデータベース設計や、負荷に強いAPI構築の現場で強固な基盤として活かすことができます。
